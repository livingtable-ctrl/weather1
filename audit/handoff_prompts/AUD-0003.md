## The problem

**Root cause:** Commit `e5331a8d` changed `cmd_order`'s live entry to `time_in_force='immediate_or_cancel'` (a taker fill) without updating the downstream settlement-P&L computation, which still hardcodes the maker-fee assumption (0.0). A pre-existing auto-path taker-cross reprice fallback shares the identical, older gap.

**Evidence (E1):** `order_executor.py:432-433` uses `KALSHI_MAKER_FEE_RATE` unconditionally; `get_filled_unsettled_live_orders()`'s SQL makes no maker/taker distinction. By contrast, `record_live_exit_fill` (`execution_log.py:734-804`) correctly uses the real fee for exits, with a comment acknowledging the IOC-specific assumption — proving the entry side was simply never updated to match. **Caution:** `tests/test_live_execution.py:983,1057,1123` currently assert the $0-fee formula as intended, correct behavior — those tests will need to change as part of this fix, not be treated as evidence the current behavior is fine.

**Files/lines:** `order_executor.py:432-433, 566-580, 989-1015`; `main.py:4702-4711` (the `e5331a8d` change); `utils.py:83,99`; `execution_log.py:535-556, 734-804` (the correctly-handled exit side, to mirror).

**Financial risk:** Overstates real live P&L for any position entered via `cmd_order` (always IOC post-`e5331a8d`) or the auto-path taker-cross fallback and closed by market settlement. This feeds `add_live_loss()`/`get_today_live_loss()`, which the daily-loss circuit breaker relies on — making the halt less likely to trip when it legitimately should, since real losses look smaller than they are.

**Recommendation (from the audit):** Track whether each order row's entry fill was maker or taker, and select the correct fee rate accordingly in the settlement formula — mirroring `record_live_exit_fill`'s existing correct treatment on the exit side.

**Audit's own noted limitation:** did not execute a live/demo trade to observe an actual taker fee charged (no credentials in this worktree); severity assumes Kalshi charges a nonzero taker fee per `utils.py`'s documented fee schedule — confirm this against current Kalshi fee documentation as part of Process step 1/2's re-verification.
