## The problem

**Root cause:** Cluster A's `cron`/`cmd_watch` unification routes `cmd_watch`'s live-position-protection through `run_trade_cycle()` only when the shared cron lock is free. The standalone `_recover_pending_orders()` safeguard that was added to `cron.py` was never mirrored into `cmd_watch`'s own flow.

**Evidence (E1):** Grep confirms exactly two real call sites for `_recover_pending_orders` (`cron.py:900-904`, `trade_cycle.py:222-226`); `main.py`'s two hits (lines 4683, 4729) are comment-only. Read of `main.py:3558-3790` confirms the `if live:` block at line 3759 is not gated on `cycle_result`.

**The narrowing (read carefully — this is the audit's own self-correction, not a weakness in the finding):** Tracing `_recover_pending_orders`'s own two sub-cases shows: (1) a pending row **with** a stored `order_id` is already independently self-healed every `cmd_watch` cycle by its own unconditional `_poll_pending_orders()` call (`main.py:3760`), regardless of lock state — no gap there. (2) a pending row **without** a stored `order_id` (the true crash-window case) cannot be resolved to a protected `'filled'` status by `_recover_pending_orders` either — it marks the row `'sent'` (a dedup-blacklist marking only), which stays excluded from the `status='filled'` filter that exit-protection actually relies on. So the originally-claimed "cron.py self-heals it within 3 hours" narrative does **not** actually restore exit-protection visibility for the one sub-case unique to the missing call — meaning the missing call's real effect is narrower than first framed. Also noted in passing: `cron.py`'s watchdog docstring says "8 min" but the actual code default is 720s (12 min) — a separate, pre-existing stale-docstring detail this finding inherited; fix it if convenient but it's not the main point here.

**Files/lines:** `order_executor.py:269-355` (`_recover_pending_orders`), `order_executor.py:1077-1115` (`_get_live_open_positions`), `order_executor.py:424-540` (`_poll_pending_orders`, filter at lines 442/455); `execution_log.py:535-556` (`status='filled'` filter); `cron.py:888-923` (early recovery call, restored ahead of exit checks), `cron.py:2346-2381` (watchdog default/docstring mismatch); `main.py:3615-3648` (`run_trade_cycle` gating), `main.py:3759-3790` (unguarded `if live:` block); `trade_cycle.py:219-226` (`_recover_pending_orders` call site); `LIVE_TRADING_RUNBOOK.md:131`.

**Real, narrower consequence:** dedup-state staleness — not an unprotected live position with real dollar exposure.

**Recommendation (from the audit):** Add a standalone `_recover_pending_orders(client)` call in `cmd_watch`'s live-order loop, mirroring `cron.py`'s own restored early call — still worth doing for consistency and to close the bookkeeping-staleness gap, just don't oversell the financial-risk framing when documenting or discussing this fix.
