## The problem

**Root cause:** `brier_score()`'s SQL has no `WHERE` clause on `condition_type`/ticker family, unlike its sibling function `count_settled_predictions()` (patched 2026-07-30), which already excludes non-temperature markets (`'between'`, `'precip_month_total'`, `'snow_month_total'`, `'hurricane_count'`, `'hurricane_next_event'`, `'storm_order'`). Shadow-logged non-temperature market families (routed via `_log_shadow_predictions()` since commits `6845b62c`/`9a7583aa`, 2026-08-06/07) contaminate the score that `brier_score()` was never updated to exclude.

**Evidence (E3 — the strongest evidence tier in the whole audit, computed directly against real production data this session):** Queried the real production `predictions.db` (read-only, via `paths.py`'s main-clone resolution) and reproduced `graduation_check()`'s exact query (the `multiday_predictions`/`outcomes_valid` join, last 50 rows by `settled_at`). Computed the Brier score two ways on the identical window: as-coded (all 50 rows) = **0.2169** (passes the 0.23 gate); temperature-only (33/50 rows) = **0.2381** (fails the gate). 17 of 50 rows (34%) are non-temperature.

**Files/lines:** `tracker.py:1917-1972` (`brier_score`, no filter), `tracker.py:2161-2232` (`count_settled_predictions`, has the correct filter — mirror this pattern), `paper.py:2778-2828` (`graduation_check`, the caller).

**Financial risk:** This is the terminal, most-decisive sub-check in `LiveTradingGate.check()`. Can silently authorize live trading when the real strategy's calibration is actually too poor, or block a well-calibrated one from ever trading. Dormant today (`LIVE_TRADING_ENABLED` unset) but structural — the bug is live right now in the sense that the gate's calculation is already wrong, it just isn't consulted yet.

**Recommendation (from the audit):** Add the same `condition_type` exclusion list already used in `count_settled_predictions()` to `brier_score()`'s `WHERE` clause.
