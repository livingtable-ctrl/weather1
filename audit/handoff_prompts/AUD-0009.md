## The problem

**Root cause:** Uses `status=='pending'` as its definition of "open position" instead of the codebase's own authoritative query (`status='filled' AND settled_at IS NULL AND closes_position_id IS NULL`).

**Evidence (E2, reproduced this session):** Read `order_executor.py:172-175` directly — matches: `sum(1 for o in orders if o.get("live") and o.get("status") == "pending")`. Confirmed `get_filled_unsettled_live_orders()` (`execution_log.py:535-556`) uses the correct, broader definition. Independently re-ran `pass11_state_repro.py::test_count_open_live_orders_drops_filled_positions` this session — **PASSED**, confirming the gap is real and currently reproducible as a passing test that demonstrates the wrong behavior (i.e., the test documents the bug, it doesn't yet assert the fix).

**Files/lines:** `order_executor.py:172-175, 1610-1613` (the `max_open_positions` gate this feeds).

**Financial risk:** Undercounts real open live positions against the `max_open_positions` gate, allowing more concurrent exposure than intended — a filled-but-not-yet-`'pending'`-tagged position simply doesn't count against the cap.

**Recommendation (from the audit):** Use the same `status='filled' AND settled_at IS NULL` definition already used elsewhere in `execution_log.py` — don't invent a third variant.
