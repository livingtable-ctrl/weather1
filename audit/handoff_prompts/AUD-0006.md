## The problem

**Root cause:** Check-then-act (`if lp.exists(): ...` followed by a plain, non-exclusive `write_text()`) instead of an atomic O_EXCL create or a real OS lock — contrast `paper.py`'s own `_CrossProcessDataLock`, which correctly uses `msvcrt.locking`.

**Evidence (E2, self-reproduced and independently re-run this session):** `audit/reproductions/cron_lock_race_repro.py` redirects `LOCK_PATH` to a tempdir and uses a `threading.Barrier` to rendezvous two threads exactly at the `exists()` check. Output: `results: [True, True]` — **both callers believe they hold the exclusive lock.**

**Files/lines:** `cron.py:205-286` (`_acquire_cron_lock`).

**Financial risk:** Two concurrent lock holders can each independently detect the same open live position needing a protective exit and each submit its own real IOC sell order to Kalshi. `execution_log.record_live_exit_fill`'s compare-and-set prevents double-*counting* P&L, but it cannot prevent the second real order from actually reaching the exchange — the gate runs after both orders are already placed. This also amplifies `was_recently_ordered`/`was_traded_today`, which are plain SELECT-then-INSERT with no DB `UNIQUE` constraint and rely entirely on this (broken) lock to prevent duplicates.

**Recommendation (from the audit):** Replace `exists()`-then-`write_text()` with an atomic exclusive create (`open(lp, 'x')`) or reuse `paper.py`'s `msvcrt`-based lock primitive directly.

**Audit's own noted limitation:** reproduced via two threads within one process (validates the code-level TOCTOU logic); a full two-OS-process repro was not attempted (not necessary to establish the flaw, but worth doing as part of this fix's test coverage if practical — see Process step 20, since a real cross-process race is closer to the actual production failure mode than a same-process thread race).
