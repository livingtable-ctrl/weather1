## The problem

**Root cause:** `status='failed'` is overloaded to mean both "genuinely never sent" (correctly excluded from dedup checks) *and* "sent, but outcome unknown because reconciliation itself also failed" (same exclusion, but wrongly — this case needs its own recovery path, not silent exclusion). No distinct status exists for the second case.

**Evidence (E1):** Confirmed `place_order()`'s `except` block re-raises only when all 3 reconciliation lookups (resting/executed/canceled) also fail or return `None`. Confirmed all 4 `execution_log` dedup functions exclude `status='failed'`. Confirmed `_recover_pending_orders` filters strictly on `status=='pending'` (so a `'failed'`-marked ambiguous row is invisible to it too). Confirmed both `_place_live_order` and `cmd_order` pre-log `'pending'` then overwrite to `'failed'` on exception — so such a row is never revisited by anything.

**Files/lines:** `kalshi_client.py:517-534` (`place_order`), `kalshi_client.py:551-608` (`_find_order_by_client_id`); `execution_log.py:278-380` (the 4 dedup guards); `order_executor.py:269-355, 1552-1685`; `main.py:4694-4756`.

**Financial risk:** A real live position could sit completely unmanaged indefinitely — no stop-loss, no exit protection, invisible to every gate that checks "open positions." A subsequent retry (by an operator or automated logic that doesn't realize a position may already exist) could double real capital exposure with neither copy protected.

**Recommendation (from the audit):** Add a distinct `'unknown'` status for this ambiguous-outcome case, with a periodic recovery routine that re-checks such rows against the real Kalshi API.

**Audit's own noted limitation:** requires a fairly specific correlated failure (the original POST fails AND all 3 reconciliation GETs also fail) — narrows practical frequency but doesn't eliminate it. Not reproduced live (no credentials in this worktree).
